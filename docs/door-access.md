# Doors, keys and secret rooms

Status: implemented foundations, October 31, 2026. [Dungeon design](dungeon-exploration-design.md) owns intended exploration rules; this document describes current behavior and authoring. The [remaining plan](specs/secret-doors-and-locks-plan.md) records follow-up scope rather than the delivered implementation.

## Runtime responsibilities

`Door` owns motion, physical collision, navigation links, interaction offers and presentation. Its explicitly assigned `DoorLockComponent` owns the mechanical lock and `SecretDoorComponent` owns concealment; both emit `Changed`, and the door refreshes its offer, marker and indicator from those signals rather than from each mutation site. Passive discovery is a separate `ProximityDiscoveryComponent` node wired in the scene to an `IProximityDiscoverable` subject (the secret door or a floor trap): the subject defines eligibility and what discovery means, the component owns cadence, sight and the roll. Shared Resources are definitions; locks, discovery clocks and saved access belong to instances. Ordinary doors have no added restriction. No new autoload or global gameplay registry is involved.

Actor-aware offers flow through the existing `InteractiveComponent` and `ActorInteractionComponent`. The latter remains the single timer/reservation owner, captures actor context, checks permission/range/line of sight and supports cancellation. Legacy door/interactive calls enter that executor. At completion, the door validates the selected method and inventory again, consumes one owned item and unlocks/opens once. Notifications observe committed state. Cancellation, wrong/missing resources and invalid reservations spend nothing.

## Keys, picking and marker

All six previously published Asset Studio key models already had game wrappers and inventory resources; they are now `KeyItem` definitions; each definition is its own identity and carries the marker color. The lockpick is a `LockpickItem`. Both stack to 20 through the existing exact-definition inventory policy. One canonical definition represents each key variety; display names or sampled colors never determine matching. Optional keys can be dropped/destroyed like normal items.

A `DoorLockDefinition` assigns `RequiredKey` and an ordered list of `UnlockMethod` strategy Resources. Each method owns its prompt, duration, permission and the item it spends; the first one the actor may use and can afford is offered, so listing the key first gives it priority. The shared `unlock_key.tres` unlocks/opens in one second with a matching key definition; `unlock_lockpick.tres` takes five seconds, requires pick capability and consumes one pick. Opening an unlocked door takes half a second and closing takes one second. A new way to unlock is a new method Resource. Unpickable keyed locks simply omit the pick method; encounter seals remain separate restrictions. Closing/reopening an unlocked door costs nothing.

Locked discovered doors show a small outlined, camera-facing diamond above the doorway in the required key's color. It is suppressed behind unexplored fog and before secret discovery, and disappears on unlock. With a matching key the prompt shows the interact glyph and “Unlock”; with only a pick it shows “Pick lock”. Without either, it shows “<key name> needed” in red with no input glyph; any actionable nearby interaction takes focus over that blocked prompt, and pressing interact on it does nothing. During the interaction, only the progress bar is shown; it has no accompanying message. Prompt textures fit their content so long names are not clipped. Key loot beams use the same palette. The marker texture/material and component references are prewired in `scenes/props/door.tscn`.

## Generation and guaranteed sources

`MapGenerator.Access.cs` owns level-local access orchestration. An explicitly assigned `LevelAccessProfile` supplies the secret pockets' door scene, lock/key definitions, detection tuning and maximum optional counts; leaving it unset retains ordinary generation. The Garrison profile makes a seeded 20% attempt for one locked room, capped at one generated locked door on the entire floor, and a separate 45% attempt for one secret pocket. Multi-entrance rooms that exceed the door budget are skipped rather than partially secured. Both chances and the independent room/door caps are editable in the Resource. Its initial key palette is gold, silver and blue crystal; the other varieties remain available for explicit authoring. Counts are upper bounds and optional placements may be omitted when geometry or key placement cannot fit.

Generated locks only lock doors rooms built: a room qualifies when every one of its doorways holds a door (room types decide that with `DoorChance`, and the door comes from the wall style), and all of them are locked together. Access never adds a door, and rejects any lock that leaves an unprotected bypass. Blocking those thresholds must preserve access to every other ordinary region, including stairs/encounter anchors. Every room is eligible except the arrival's and the gatekeeper's, secret pockets and rooms holding stairs or other progression anchors. Explicit locks and secret thresholds also block key-source validation.

One guaranteed matching-key pickup is reserved per physical locked door in space reachable from entry without any generated lock, secret or pick. Multiple same-color doors therefore have sufficient quantities. Key sources use stable source IDs and the existing item-baseline/delta persistence; spending keys does not regenerate their pickups on revisit. Lockpicks never spawn as generated floor supplies. Only the Rogue starts with two; future shop stock is deferred. Other classes start without picks. Matching keys remain the guaranteed solution for generated locks. Source positions avoid furnishing, occupied columns and other loot; later random loot respects their reservations. Key placement is independent of random loot tables and normal inventory capacity still applies. Generated dependency chains and mandatory mechanical locks are excluded. Required large-encounter space is reserved before optional locks, and final gatekeeper placement filters inaccessible regions. Teleport destinations also exclude locked and undiscovered regions to avoid stranding the player.

Secret pockets are planned before furnishing at variable existing corridor or room wall segments. Each has a narrow entrance and a 3x3 interior. A candidate requires an existing full straight wall, space for the pocket and no unprotected neighbor connection. Existing ordinary wall mesh, orientation and collision remain untouched until discovery; no special secret-wall tile is required. Full wall variants, including protruding variants, are accepted. Structural corners/partial pieces are unsuitable hosts. Adding optional pockets cannot create a bypass between existing locations.

## Discovery and visibility

Successful live discovery briefly glows yellow while the actual original floor/wall mesh crossfades into the trap plate or closed door. The shared, Inspector-authored surface effect defaults to 0.6 seconds; duration, color, strength and blending are adjustable. It fades private copies of surface materials (including on the Mobile renderer), restores original material assignments/visibility, then removes its temporary geometry. The original surface warms up before the discovered mesh begins appearing. No ring, persistent highlight or discovery text remains, and restoration never replays the effect. The original floor collider stays intact throughout a trap reveal; a secret door remains physically closed throughout its reveal.

Floor traps use the same detection policy, primary attribute, half-second clock, height limit and unobstructed approach checks as secrets, from any side. Their separate `trap_detection.tres` profile has a 12-unit radius, twice the secret-door radius, to allow earlier warnings. Only explored trap locations are eligible. Finding one reveals its plate; it does not trigger or disarm the trap. Stepping on an undiscovered trap exposes it through the spike attack itself. Existing damage, cooldown and rearming remain active after discovery. Known trap identities persist through floor regeneration and save/load; cooldowns remain transient.

Each concealed opening checks every 0.5 seconds of active gameplay while the player is within the profile's radius (default six units), compatible height and accessible approach side. A ray must reach the actual concealed wall, allowing its own thickness while rejecting intervening geometry. Default chance is 10% at Intelligence 10 plus one percentage point per additional point, capped at 90%. The profile can select another primary attribute. The clock runs only while the subject is findable, pausing stops it and slow frames do not produce catch-up bursts. Standing nearby continues to roll.

Discovery permanently reveals a closed door, without opening/unlocking it or revealing the destination. No interaction prompt, key marker, door x-ray, navigation bridge or exploration sight crosses an undiscovered opening. Loot and x-rays share `ExplorationVisibility`, which resolves both generated content and drops under the level runtime root. Undiscovered pickups hide their entire subtree (model, glow, sparkles, light, labels and x-ray helpers), stop particle emission and block collection. Nameplates (names and health bars) draw over the fog caps that conceal ordinary actors by depth, so they check discovery themselves and stay hidden until their own tile is explored. Initializing level content stays hidden until exploration is available; standalone previews remain visible. Magnet pickup cannot pull items through intervening walls. Revealed closed doors continue to block traversal. Opening enables the existing navigation link and ordinary line-of-sight discovery.

`SecretDoorComponent.Reveal()` is idempotent and callable by a future mechanism. Removing or disabling a door's `ProximityDiscovery` node leaves a button-only secret. Hidden-button content and mechanism authority to unlock/open are not implemented yet.

## Interior cell gates

`InteriorDoorComponent` is an explicitly wired optional capability on `Door`. It owns a stable room-local ID, gate opening width and furniture clearance for the hinge sweep and approaches. The normal `Door` interaction, cancellation, animation, collision and navigation link handle each gate. The reusable barred gate scene uses the existing dungeon kit's iron door mesh; each room instance owns its sized collider.

The prison room type's `CellsStep` emits shared barred dividers, front pieces, corner and junction pieces and one gate per cell along one or two opposing long walls. A row starts flush in a room corner when it fits (the side wall closes its first cell), keeps its far end free for the entrance, and keeps each gate's swing clear of furniture. Its cells are unlocked and non-secret. Every usable floor area must connect with the gates open. The navigation bake includes the closed gate collider; opening enables the normal doorway link. Bars do not seal exploration into cells.

Interior gates receive identities scoped by placed room and local cell ID. They do not register as exterior connectors or participate in optional room-lock assignment. Their normal door baselines and open-state deltas survive floor regeneration/save restore. Discovery can show their indicators independently of the exterior connector sight rules. Internal mechanical locks and opaque partition visibility remain future work.

## Persistence and randomness

Access placement and discovery use independently derived streams, isolated from layout, encounters and source loot. Stable ordering and identities reproduce untouched access configuration for the same build/content/seed. Runtime discovery draws are not replayed after reload; actual discoveries are saved.

Save data stores discovered/locked/current-open deviations by stable connection identity and discovered trap IDs, separately from the exact explored tiles. Revisiting an explored branch does not open a door the player closed. Restore preflights identities and state combinations, applies access and item differences before normal gameplay, and reveals only saved exploration. No half-completed picking channel resumes. Changes require the current `SaveGame.CurrentVersion`; earlier development saves require a new run, with no migration.

## Authoring and verification

Assign `AccessProfile` on a level's MapGenerator to enable generation. For an authored lock, assign a definition to the prewired `DoorLock` child and set a canonical required key/pickability/duration. Mark `LockEligible` only when automatic optional-room locking is appropriate. Unassigned optional capabilities stay absent; regeneration applies Resource changes. Do not mutate shared definitions during play.

Regression coverage exercises consumption, wrong colors, key preference, stack round trips, interruption/tool loss, reservations, markers, all six published models, deterministic generation, reachable quantities, accessible sides and regenerated saved access. Existing timed-interaction/loot tests remain relevant. Windowed review checks marker readability and concealed/revealed wall appearance; real navigation across a generated secret is checked separately because headless path tests are unreliable. Probability, optional counts, detection radius, reward density and monster pressure still need playtesting.

The [world-effect harness](../scenes/debug/README.md#world-effects) previews the production trap/secret reveals, loot glow and blood hit without needing to find them in a generated floor. Use it for visual tuning; runtime tests check effect completion, material cleanup, floor preservation and repeatable replay.
