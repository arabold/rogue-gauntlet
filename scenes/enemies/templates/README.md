# Monster starting assemblies

Duplicate `melee_enemy.tscn` or `projectile_enemy.tscn` in the Godot FileSystem dock and save it in your monster folder. Its actor root is independent (not inherited from another enemy); component and model scenes remain reusable instances. Delete/add optional capability nodes in the Scene tree. Keep the required references assigned on the root and on each component.

Save the definition as a new `.tres`, give it a unique ID/display name and edit health, speed, XP and loot there. Make the behavior and its tactical/movement/attack/defense policies unique before changing values for only this monster. Changing a shared Resource intentionally changes every user of it. Assign a replacement visual/animation binding and adjust the body and hurtbox shapes to match.

Use Project > Tools > Validate monster scene to inspect the open actor. Validation is read-only and reports missing references, capabilities or clips in the Output panel. The shared action gate must be authored; definition-driven actors do not create it at runtime. Add the finished actor scene to a realm encounter pool to make it appear in gameplay.

`mobile_enemy.tscn` is the unfinished common assembly for different rigs. It intentionally has no model, collision shapes, definition or attack animation profile and will not pass validation until those are assigned. Use either complete example for a playable starting point. The projectile example uses maintain-distance movement and one projectile policy; it has no melee fallback. Both examples prewire the shared `humanoid_vulnerability.tres` and a `PoiseComponent` on the hurtbox; make its definition unique to tune hit reactions, or delete the node and clear `HurtBoxComponent.Poise` for an actor that every hit interrupts. Add guard or dodge to either example by assigning the capability, definition/animation, action gate and defense-controller references explicitly, then matching the defense probabilities.

Shared Resource changes apply to newly initialized actors; arbitrary live editing is not supported. Components own health/action/cooldown state separately for each instance. See [design](../../../docs/monster-authoring-design.md) and [current system](../../../docs/development-roadmap.md#first-three-floor-acceptance).

Authored component dependencies are explicit Inspector assignments. The warrior root references its guard, dodge, defense controller and attack controller; its defense controller references the assigned guard/dodge. Empty optional references stay unavailable to that consumer, even if another component exists in the scene. The controller uses the AI target dynamically; it does not discover defense capabilities at startup or during processing. Validation reports missing required connections.

The behavior must explicitly assign a TacticalStrategy. Customize its retreat deadline, retry delay, stand-and-fight distance and optional intervening attack requirement in the Inspector. Runtime selector state is created independently per actor; editing a shared Resource affects future actors. The projectile example shares the crossbow policy until you make it unique.
