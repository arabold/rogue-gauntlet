## Testing
- C# tests use **GdUnit4** (`gdUnit4.api` + `gdUnit4.test.adapter`). Tests live under `tests/` and are compiled into the game project itself — GdUnit4's `[RequireGodotRuntime]` tests boot a real Godot instance, which only works when the test assembly shares the game's `project.godot` and `res://` tree, so a separate test project is not viable here.
- Run tests: `dotnet test "Rogue Gauntlet.csproj" --settings .runsettings`. Export `GODOT_BIN` first so GdUnit4 can find the engine (the path is intentionally kept out of `.runsettings` for portability), e.g. `export GODOT_BIN="/Applications/Godot_mono.app/Contents/MacOS/Godot"`. The adapter generates a runner scene under `gdunit4_testadapter_v5/` and hosts runtime tests in that engine instance, launched with `.runsettings`' `GdUnit4.Parameters`: `--headless`, so no window steals focus (headless renders are blank, so don't assert on rendered pixels), and `--fixed-fps 60`, so tests run in simulated time: every frame advances exactly 1/60 s of game time with one physics tick, as fast as the machine allows, and a run is deterministic. `tests/BannedSymbols.txt` makes the wall-clock waits a compile error. Wait in game time: `TestFactories.AwaitPhysicsUntil` for an outcome, `AwaitPhysicsSeconds` for a timed duration, `AwaitPhysicsFrames` to settle a frame or two or to step a loop; never `runner.SimulateFrames(n, ms)`, `AwaitMillis`, `Task.Delay` or a `Stopwatch`, which sleep on the wall clock while an unknown amount of game time passes. `runner.SimulateFrames(n)` is n game frames. Gameplay timers count frames too (process or physics deltas, or `FrameClock.Seconds`), never `Time.GetTicksMsec()`, so they run the same in simulated-time tests and Movie Maker recordings as in play.
- The test dependencies, the test sources, and the generated runner are all scoped to the **Debug** configuration in `Rogue Gauntlet.csproj`, so exported builds (`ExportDebug` / `ExportRelease`) stay clean — verify with `dotnet build "Rogue Gauntlet.csproj" -c ExportRelease`.
- Test classes use `[TestSuite]` / `[TestCase]` and the `GdUnit4.Assertions` static helpers. Tests that touch Godot resources, nodes, or the scene runner must add `[RequireGodotRuntime]`; plain-C# tests omit it and run far faster (no engine boot).
- Only the .NET 10 runtime is installed locally, so `.runsettings` sets `DOTNET_ROLL_FORWARD=LatestMajor` for the testhost (scoped to the test run, so normal Debug gameplay stays on its declared TFM). The first runtime-test run is slow because Godot imports the checkout's assets — warm it with a headless boot if the runner times out, or raise `GodotConnectTimeout` in `.runsettings`.
- Concurrent test runs from different checkouts/worktrees collide: the adapter and its Godot instance talk over a fixed-name .NET pipe (`gdunit4-message-pipe`), a socket file in `$TMPDIR`, so parallel runs connect to each other's engine, hang, or fail with "The server returned an unexpected status code" and can leave orphaned runner processes. Give each run its own short temp dir (macOS caps socket paths at 104 chars), e.g. `mkdir -p /tmp/gdu-<worktree> && TMPDIR=/tmp/gdu-<worktree>/ dotnet test ...`.
- All runtime suites share one Godot instance, so autoloads (`SignalBus`, `GameSession`) outlive each test. Never call `_Ready()` by hand on a node outside the tree: `SubscribeUntilExit` unhooks `SignalBus` handlers only on tree exit, so freeing that node leaves a dead handler that throws on every later emit and skips every subscriber after it, breaking unrelated later suites. Use `TestFactories.AddToSceneTree(node)` instead.
- Load test scenes with `TestFactories.LoadScene(path)` and resources with `TestFactories.Load<T>(path)` (it takes the same `cacheMode`), never `ISceneRunner.Load`, `GD.Load` or `ResourceLoader.Load` directly; `tests/BannedSymbols.txt` makes those a compile error under `tests/`. Back-to-back reloads, such as parameterized cases loading the same path, hit a Godot .NET race (godotengine/godot#83762): a cached resource whose C# wrapper was collected but not yet finalized is revived as null, and the finalizer then aborts the engine with `FATAL: Condition "gchandle.is_released()"`. The aborted engine keeps running without reporting, so the run looks hung on the next test until `--blame-hang` gives up. Both helpers first settle pending finalizers through `ResourceCacheGuard` (about 12 ms per call), as `Level.Generate()` does before each floor. Drop the guard and the ban once the engine fix ships.
- Enemy navigation runs on the floor's `ClearanceGrid` (plain C#, no navmesh), so it is testable headless: unit-test grids and fields directly (`ClearanceNavigationTest`) and drive real monsters on generated floors in game time (`MonsterChaseTest`).
- Test observable outcomes, not private state, node wiring or values that only mirror a `.tres`; a test that restates the code or the data adds runtime without catching anything.
- Keep the suite fast:
  - Every `TestFactories.Load` forces a GC to settle finalizers, so load each resource once per test into a local, never through a property getter inside a loop.
  - Simulated time is CPU-bound, so long game-time waits are cheap but not free. Wait for the outcome (`AwaitPhysicsUntil`) instead of a long fixed frame count, and stage independent scenarios side by side in one world instead of one after another.
  - Generate a floor once and check every invariant on it (`GeneratedFloorSweepTest`) rather than regenerating the same seeds per invariant. Load the shipped level with `TestFactories.LoadLevelScene()`, `LoadLevel` or `GenerateLevel`, and regenerate it in place with `TestFactories.Regenerate(level, seed, depth)` rather than loading it again.
  - Floor generations dominate the run; a combat-harness load costs about 0.2 s, so merge harness tests only when that also removes a wait or a duplicate check.
- Spawn combat-harness monsters with `TestFactories.SpawnHarnessMonster(harness, scenePath)`. Harness commands name items, spells and monster scenes by `res://` path, never by list position.
- Drive debug actions through the tools, not hand-rolled setup: `TestFactories.Tool<T>(scene)` finds a scene's `ItemSpawnTool`, `MonsterTool`, `SpellCastTool`, `HeroTool`, `CombatDisplayTool` or `LevelTool`, and `TestFactories.Press(menu, text)` clicks a menu entry when a test covers the menu itself.
- `dotnet build "Rogue Gauntlet.sln"` remains the fast compile check; add a `dotnet test` run when changing testable C# logic.

## Save Games During Development
- Until the game is publicly released, save compatibility between versions is explicitly out of scope. Breaking existing development saves is allowed.
- Do not add save migration code, legacy DTO fields, old-format adapters, or fallback reconstruction to preserve saves from earlier versions.
- Use `SaveGame.CurrentVersion` to identify the supported save format. Bump it when save schema, authored content, or generation changes make existing saves incompatible; reject mismatched or missing versions with a clear message that a new run is required. Do not attempt conversion.
- Current-version save/load must still preserve supported runtime state correctly. Rejecting an incompatible save must not silently overwrite it. Compatibility requirements should be revisited before public release.

## Architecture
- Autoload singletons are declared in `project.godot`: `SignalBus` (`scripts/SignalBus.cs`), `GameSession` (`scripts/GameSession.cs`), `ScenePool` (`scripts/ScenePool.cs`), `LoadingScreen` (`scenes/ui/loading/loading_screen.tscn`), `SceneDebugBootstrap` (`scripts/SceneDebugBootstrap.cs`), and the GDScript Phantom Camera manager.
- `GameSession` is the focused session-flow coordinator: save slots, run identity and level transitions. Run-wide state lives in a plain `RunState` (`scripts/RunState.cs`: run seed, loot counter, cleared entities, item identification) that it hands to each `Level`; it is intentionally *not* a generic gameplay registry. Gameplay code gets run and floor context from its `Level` (`Seed`, `Depth`, `Run`, `Floor`, `Discovery`), resolved once in `_EnterTree`, never from the autoload. `ItemIdentity`'s UI-wide display is the one documented exception.
- `Main.cs` binds screen effects and the death screen and has `GameSession` configure the `Level` before `Level.Generate()`; the `GameCameraRig` (`scenes/main/camera/game_camera.tscn`) follows the hero; `MapGenerator.cs` (with its `.Access` and `.Loot` partials) owns room layout, corridor connection, gridmap merge, access, loot, navigation grid, and spawn-point creation, and hands gameplay a frozen `GeneratedFloor`. See `docs/level-design.md` for the full generation pipeline.
- Do not add a `GameManager`-style gameplay registry; use local dependencies, signals, or local group queries instead.
- Debug actions exist once, as `DebugTool` nodes hosted by the HUD's `DebugMenu` (`scenes/ui/debug/`), acting on the menu's `IDebugWorld`: a `Level`, or the `DebugArena` at the root of the combat or room harness. A harness hosts that same menu and adds only its own readouts and staging; never give a harness a second set of item, spell, monster or display controls. Rooms and trap gauntlets are played in the room harness (`scenes/debug/rooms/`), whose picker builds any room type the generator can, and floors in the map harness (`scenes/debug/maps/`); there is no trap-staging tool, so tests stage single hazards themselves (`tests/TrapStaging.cs`). New content under the tools' and harnesses' folders shows up without code changes. See `scenes/debug/README.md`.
- UI looks live in the project theme (`scenes/ui/theme.tres`): pick them with Theme Type Variations (`FramePanel`, `PrimaryButton`, `HeaderLabel`, ...), not per-node style, font or color overrides; frame, slot and ornament art comes from the generated kit (`asset-studio/ui/ui_kit.py` → `assets/ui-kit/`), the theme itself is built by `asset-studio/godot/build_ui_theme.gd`, and animated shapes are `[Tool]` controls in `scenes/ui/widgets/`. Never mix in third-party UI kits. In-game UI stays muted and see-through (bare readouts, translucent slots); the carved `FramePanel` is for full stops: death and confirmations. See `docs/user-interface.md`.
- Decoupled game/UI updates go through `SignalBus` static emit helpers. Add new bus events there instead of introducing direct cross-system references when reacting to gameplay state.
- Player behavior is component-scene based: `Player.cs` exports its components (`MovementComponent`, `InputComponent`, `HealthComponent`, `HurtBoxComponent`, `ActionManager`, attack and inventory controllers) and `player.tscn` wires them; it injects only runtime state such as the per-run inventory copy.
- Data authored in Godot resources matters: items, player stats, dungeon factories, mesh libraries, and rooms are `.tres`/`.tscn` assets under `scenes/`; C# changes often need matching exported properties/resources in scenes.

## Architecture & Godot C# Guidelines
Use the `godot-csharp` skill (`.agents/skills/godot-csharp/SKILL.md`) whenever writing or refactoring C# gameplay, component, UI, or Resource scripts.

- **Seeded Determinism & Persistence:** Reconstruct untouched dungeon content from the run seed and derived RNG streams (`GenerationRandom.DeriveSeed`); persist deviations rather than full floor snapshots. Keep layout, monsters, source loot, gameplay-time randomness, and cosmetic streams separate. Reproducibility is required for the same build/content and inputs; bump `SaveGame.CurrentVersion` when changed generation invalidates saved deltas.
- **Physical Combat Contact:** Confirmed combat contact has no passive accuracy/evasion roll. Avoidance comes from movement or timed dodge/guard/parry components; armor mitigates damage.
- **Composition, Strategy & Factory:**
  - **Composition:** Build actors from single-capability child `Node` components (`[GlobalClass]`) wired via `[Export]` in `.tscn`. Actor roots (`Player`, `EnemyBase`) stay thin facades. Split classes only when they own multiple independent reasons to change.
  - **Strategy:** Vary behavior via selectable `[GlobalClass] public abstract partial class ... : Resource` strategies (one `[GlobalClass]` per `.cs` file) exported on components or definitions. Keep shared `.tres` strategies stateless; pass actor context into methods or create a per-actor state object in `_Ready()`.
  - **Factory & Prototypes:** Treat authored `.tres` assets as immutable definitions. Clone runtime state in `_EnterTree()` (`CreateRuntimeCopy()` / `Duplicate()`) before child `_Ready()` runs, and encapsulate spawning/loot rolling in Factory classes or `[GlobalClass]` factory resources instead of hardcoded `res://` paths.
- **Editor-First `[Export]` Authoring:**
  - **Expose `[Export]` properties (`{ get; set; }`), never C#-only `GetX()`/`SetX()` or `{ get; private set; }`:** Tunable attributes (`Speed`, `MaxTurnRate`, `Duration`, `Xp`), configurable actor states (`InitialAction`, `AIEnabled`), and Node/Resource dependencies must be `[Export]` properties so the Inspector, `.tscn`/`.tres`, Remote Scene Tree, and `AnimationPlayer` tracks can bind them directly.
  - **Reactive `[Export]` setters:** Put side effects (clamping, child updates, state transitions) in the `[Export]` property's `set` accessor, guarding scene/child updates with `if (!IsNodeReady()) return;` because Godot assigns exports during deserialization before `_EnterTree()` and `_Ready()`.
  - **Explicit Inspector wiring:** Do not discover authored dependencies via `GetNode("...")` or silently refill empty optional exports in `_Ready()`. An unassigned optional export disables that capability; validate required references explicitly. Default-initialize exported arrays (`= [];`).
  - **`[Tool]` Inspector polish:** Guard runtime logic with `if (Engine.IsEditorHint()) return;`, use `[ExportToolButton]` for Inspector action buttons, `_GetConfigurationWarnings()` for missing-reference badges, and `_ValidateProperty` + `NotifyPropertyListChanged()` to hide mode-irrelevant fields.
- **Three-Tier Notification Model:**
  - **Local component events -> `[Signal]` delegates:** Declare `[Signal] public delegate void ...EventHandler(...)` with Variant-compatible parameters and emit via `EmitSignal...()`. Use a plain C# `event` only for non-Variant structs (`in DamageContext`).
  - **Observed Resources -> `ObservableResource`:** Call `SetValue(ref _field, value)` inside `[Export]` setters so code and Inspector edits emit `EmitChanged()`.
  - **Cross-system broadcasts -> `SignalBus`:** Reserve `SignalBus` static emit helpers for decoupled cross-system notifications, never feature logic or fallible request/response calls.
  - **Subscription lifetime (`SubscribeUntilExit`):** Wrap subscriptions to long-lived emitters (`SignalBus.Instance`, runtime `Resource`s, `SceneTree`, ancestors) in `this.SubscribeUntilExit(...)`. The subscription holds only while the node is in the tree: leaving unhooks it and re-entering (pool reuse, `Reparent`) restores it. Connect to a node's own children with a plain `+=` in `_Ready()`.
- **Queries & Contracts:** Prefer C# interfaces (`IDamageable`, `IInteractive`, `IPlayerAction`) for type-safe contracts and local Godot group queries (`player`, `enemy`, `damageable`) over global registries or service-locator autoload lookups.

## Godot/C# & Mobile Renderer Gotchas
- **One lighting model:** a world (a `Level`, a harness `DebugArena`, a workbench) implements `ILitWorld` and owns one `WorldLighting` (`scenes/levels/lighting/world_lighting.tscn`, the game's shared environment and **Dark level** switch). The hero's light and torches find it through their ancestors, and monsters find navigation the same way through `INavigableWorld`. Never add a `WorldEnvironment` or `DirectionalLight3D` to a harness or workbench; a subject without a playing hero gets `scenes/player/player_light.tscn` beside it. Stand subjects on `scenes/debug/stage/sample_floor.tscn`, and use `scenes/main/camera/game_camera.tscn` for the game's view.
- **Mobile Renderer (`rendering_method="mobile"`) & Transparency:**
  - Never use `GeometryInstance3D.Transparency` (Forward+-only; fails silently on Mobile).
  - For standard fades (`FadeOutComponent`), duplicate each surface's `BaseMaterial3D` into an instance-local override (`TransparencyEnum.Alpha`) and tween `albedo_color:a` (plus `modulate:a` on `SpriteBase3D`/`Label3D`) so shared materials are never mutated.
  - For multi-mesh actor shader fades (`teleport_depth.gdshader` + `teleport_surface.gdshader`), use a two-pass `ShaderMaterial` (`NextPass`): an invisible depth pre-pass (`blend_add, depth_draw_always`) followed by the color fade pass (`blend_mix, depth_draw_never`). Keep solid skin overrides on opaque depth (`depth_draw_opaque` / `AlphaScissor`) via `SurfaceAppearanceController`.
- **Floor markers:** a dungeon floor's visible surface is not its plane: tiles top out about 0.05 above it, rocky and decorated ones up to about 0.2, and rugs, inlays and stairs rise further, while harness floors hide this. Draw every flat marker on the floor (attack warnings, landing rings, area previews) with `scenes/effects/shaders/ground_overlay.gdshader`, or include `ground_overlay.gdshaderinc` in its own shader; never lift it by a small fixed height. Check a new marker on a generated floor, not only in a harness. Solid props stand on the measured surface instead (`MapGenerator.GetFloorSurfaceHeight`).
- **Tool scripts:** the editor runs only `[Tool]` scripts and hands every other C# node or Resource to them as a plain placeholder. Every type a tool script exports or fetches by type (`GetNode<T>`) must be a tool script too; mark plain data Resources `[Tool]`, and guard nodes whose code must not run in the editor with `Engine.IsEditorHint()`, setters included, since the editor re-sets exports when it reloads the assembly. In code that runs in the editor, connect signals by method (`+=` in `_EnterTree`/`_Ready`, `-=` in `_ExitTree`), never through `SubscribeUntilExit` or a lambda: the editor reloads the C# assembly after every build and cannot restore closures, so their callables fail with `delegate_handle.value is null` on the next emit, such as `tree_exiting` when the scene closes.
- **Physics engine:** 3D physics runs on Jolt (`physics/3d/physics_engine`); GodotPhysics3D deadlocked bodies resting on a floor GridMap while touching a convex wall, and is being phased out upstream.
- **Runtime Lifecycle, Physics & Pooling:**
  - Set `ProcessPhysicsPriority` from `CombatPhysics` in `_Ready()` whenever `_PhysicsProcess` order matters; call `SetPhysicsProcess(false)` when idle.
  - Check `GodotObject.IsInstanceValid(node)` (not just `!= null`) on dynamic runtime `Node` references held across frames, tweens, `ToSignal`, or `CallDeferred`.
  - Load boundaries settle the godotengine/godot#83762 race with `ResourceCacheGuard.Settle()` (floor generation, harness and debug-catalog loads). The startup scene's load has no boundary, so `GameSession`'s constructor suspends collections until the autoloads are ready (`ResourceCacheGuard.BeginStartup`/`EndStartup`); without it the combat harness aborted on launch whenever new code shifted GC timing.
  - Use `ScenePool.Spawn<T>` / `ScenePool.Despawn` for short-lived combat/VFX scenes and reset per-spawn state in `IPooledNode.OnSpawnedFromPool()`.
  - Call `ResetPhysicsInterpolation()` after snapping a `Node3D`'s `GlobalPosition`/`GlobalTransform` (`physics_interpolation=true`).
  - Defer physics state changes (`SetDeferred` / `CallDeferred`) inside `BodyEntered`/`AreaEntered` callbacks, kill previous `_activeTween?.Kill()` before replacing a tween, and cache `StringName`s on hot paths.
- Godot C# partial classes are in the global namespace in existing code despite the csproj root namespace; follow the current pattern unless doing a deliberate namespace migration.
- Keep scene/resource paths lowercase as authored (`scenes/main/main.tscn`); there is at least one stale mixed-case reference in code (`Main.tscn`) that should not be copied.
- **Naming, Taxonomy & Shims:** Follow the `program-design` skill (`.agents/skills/program-design/SKILL.md`) for naming rules: use `*Profile` for configuration resources, `*Component` for actor capabilities, direct domain nouns for actors/props, enforce subject-first asset and scene naming (`torch_flame.tscn`, `brazier_fire.tscn`), and never introduce backward-compatibility shims or legacy aliases.
- Phantom Camera is GDScript-only here; `GameCameraRig` positions its `PhantomCamera3D` as a plain `Node3D` and never calls its GDScript API.
- `.editorconfig` sets tabs for `*.cs`, CRLF, and no final newline; match local formatting when editing C#.

## Coding Principles
- Follow DRY, KISS, YAGNI, and SOLID; prefer the simplest solution that works.
- Use the latest version of the language, libraries, and the Godot SDK. Current Godot/C# docs are available — consult them rather than guessing at API surface.
- Add and update documentation for classes, methods, and functions, focused on functionality and reasoning. Skip documenting individual parameters/return values whose use is obvious from their name.
- Keep `README.md` and `ARCHITECTURE.md` as the sources of truth for project overview and architecture; consult them for current context.
